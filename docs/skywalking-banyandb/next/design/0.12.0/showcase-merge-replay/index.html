Merge replay using captured showcase data

Status: the stream/measure whole-block copy optimization was reverted on 2026-11-23. The separate measure timestamp-boundary fix, trace secondary-index improvement, and general merge benchmarks remain. The comparisons below describe the preserved experimental revisions, not the current stream/measure implementation.

The follow-up diagnosis reproduces the modest measure improvement and does not reproduce the earlier stream slowdown. It identifies limited copy coverage, an overly conservative history check, and existing allocation problems in ordinary merging. The initial measurements are retained below, followed by the controlled comparison.

Measurement and validation

Use Go 1.26.11 on Linux amd64, local ext4 storage, GOMAXPROCS=4, and GOMEMLIMIT=3GiB. The latter is a Go soft memory target, not a container memory limit. The host has 32 logical CPUs and runs unrelated services, which remain untouched. Serialize all replay processes and finish builds and downloads before timing. Alternate base/change order over three pairs: base/change, change/base, base/change. Stream receives three additional pairs because its initial elapsed time increased while CPU time decreased; report all six pairs, including the original samples. Each run starts a fresh process and writes a fresh output directory. The logs preserve the actual order and the pause for the measure version audit.

Read and checksum the input files before each run. These are warm local-cache measurements; they do not establish cold-storage or cloud production latency. Time tsTable.mergeParts for stream/measure and state.Merge for the secondary index, including output flush/sync and metadata publication. Exclude input setup, post-merge verification, external sorting, and report generation.

Record wall time, process CPU time, Go allocations, output bytes/blocks, and process peak RSS sampled immediately after merging. RSS includes startup and input opening; it is not a resettable merge-only heap measurement, and excludes later validation memory.

Reopen every output and decode every row. Hash series IDs, timestamps or keys, versions or element IDs, and all typed field/tag values. Separate untimed runs collect stream/measure copied-block counters and must produce the same decoded output as the measured runs.

Measure version audit

The initial exact row-multiset comparison deliberately stopped on a difference: base stores 58,080,044 rows and the revised merge stores 58,080,011. Comparing only row counts would not establish that this difference is correct.

Both outputs contain overlapping blocks, so a scan in physical file order is insufficient to select the newest version. Export fixed-width records containing series ID, timestamp, version, and the already verified canonical row hash. Externally sort those records with bounded memory, then select the greatest version for each key independently of the production merge implementation.

Both outputs contain 58,076,680 distinct keys, with identical newest-version values and no conflicting payloads at an equal winning version. The ordered winner-row SHA-256 is 67906ce250a4e7965d9bd892e5328ce81735592926b430995ed2b5819a5a51dc. Base retains 3,364 strictly older rows; the revised merge retains 3,331. There are 3,300 common older rows, 64 present only in the base output, and 31 present only in the revised output. Thus the change leaves 33 fewer older rows overall; it does not simply remove the same 33 records from an otherwise identical physical layout. Neither implementation globally removes every older version across overlapping output blocks.

Targeted decoding of 187 original input blocks confirms that all 95 differing older-row hashes exist in the captured inputs, with no missing or altered payloads. Later repetitions must match the audited raw row multiset for their own revision exactly. This retains a strict check without incorrectly demanding identical physical retention of superseded versions.

Retained evidence and replay method

The captured observability data and replay harness are not distributed with this repository. Repeating these exact measurements requires both the capture and the frozen implementations. For runnable repository fixtures, use the synthetic merge benchmarks.

The retained harness-and-evidence.tar.gz archive has SHA-256 6acd4194beb2d615c6b7dbf0b74d8fc0025c4fe9d2530e248dcdcaa8bc229c32. This identifies the evidence, not a public download. It preserves the frozen binaries, audit tools, package sources, build overlays, and generated-code prerequisites; captured inputs and merged outputs are stored separately. capture.json and each input’s source.json record snapshot paths and part lists. Before/after checksum manifests record the source-file hashes, while production-provenance.json records source hashes and the environment.

The replay driver pre-reads inputs, runs one binary at a time, saves its invocation and binary hash, and validates the output before starting the next run. The initial comparison uses six stream pairs, three measure pairs against the audited reference, and three secondary-index pairs. Separate diagnostic runs count shortcut eligibility without contributing to the timing samples.

Run directories must be new; use a fresh capture/output root for a repeated experiment. Each output retains report.json, validation.json, the persisted part, and decoded row hashes. Top-level run logs and invocation records preserve failures as well as successes. The stream/measure semantic hash uses LC_ALL=C sort --parallel=1 -S 256M followed by SHA-256; the trace harness uses a 128 MiB sort buffer. Neither removes duplicate rows.

The measure audit is separate from timing. Its source and build overlays are retained in the measure harness folder; oracle-comparison.json, input-loser-validation.json, and loser-key-differences.json record the aggregate findings. Each first-pair run retains sorted-version-oracle.json. The audit sorts 116-byte key/version/hash records with a 512 MiB buffer and two sort workers per output, then streams them through a constant-memory version selector. Builds and all audit work finish before timed runs resume.

Follow-up: explain the small measure gain and stream slowdown

The whole-block shortcut has limited coverage in these captures. It also has a conservative history check that excludes additional measure candidates. The original stream elapsed-time increase must be assessed separately from those algorithmic limits: CPU fell slightly, three of six paired runs became faster, and three became slower. The difference of medians (+5.7%) is not a stable estimate of a regression. The mean paired difference was +0.115 seconds.

Controlled comparison

Build four versions using temporary Go overlays, without changing production sources:

  1. Original base 959a4d76.
  2. Revised code with tryCopyBlock returning false before any eligibility work.
  3. Revised code running all eligibility checks and lookahead, then returning false before copying.
  4. Full revised code.

Versions 2–4 retain the strict timestamp-boundary correction. Comparing 2 and 3 isolates eligibility overhead; comparing 3 and 4 isolates copying after checks. Comparing the original with version 2 also includes the other small supporting changes, so it is not a pure equality-fix microbenchmark.

Use eight rounds per stream variant and four per measure variant: 48 timed replays. Each round rotates a seeded variant order; the second four stream rounds reverse the rotations. Every process has GOMAXPROCS=4, a 3 GiB Go soft memory target, and CPU affinity 8–11 (four distinct cores, not exclusively reserved). Inputs are checksum-read before every process. Output is fresh and uses the same local ext4 filesystem. Other services remain untouched.

All variants include identical low-frequency timers around actual file sync calls. Close time includes buffered flushes and some of those syncs, so close and sync durations must not be added. CPU profiles and eligibility counters are collected in separate runs and excluded from the timing table.

Variant Stream elapsed median, s Stream CPU median, s Measure elapsed median, s Measure CPU median, s
Original 4.856 5.203 38.230 43.125
Revised, copying off 4.837 5.112 38.591 43.435
Revised, checks only 4.822 5.221 38.577 43.179
Revised, copying on 4.749 5.052 35.772 40.338

Original → revised median changes are -2.2% elapsed / -2.9% CPU for stream, and -6.4% elapsed / -6.5% CPU for measure. Revised stream is faster in seven of eight paired elapsed-time comparisons and all eight CPU comparisons. Measure is faster in all four comparisons. These are results for the captured inputs, not a guarantee for other data or the production scheduler.

Checks-only versus copying-off has no clearly resolved CPU penalty: the mean paired difference is +0.042 s for stream and -0.062 s for measure. Exploratory 95% paired-bootstrap intervals include zero (stream -0.083 to +0.152 s; measure -0.407 to +0.186 s). Those small sample intervals are diagnostic evidence, not universal performance bounds. Enabling copying after checks saves a mean 0.122 CPU seconds for stream and 2.977 CPU seconds for measure.

The earlier stream slowdown is not reproduced. Sync time across the quiet stream runs ranges from 0.094 to 0.625 seconds, larger than the useful saving. For example, round 2 uses 5.089 → 4.980 CPU seconds but 0.319 → 0.438 sync seconds. Elapsed time consequently moves from 4.767 to 4.795 seconds. A slower elapsed result can therefore coexist with less computation. The original runs had no sync breakdown, so their individual delays cannot be attributed retrospectively with certainty.

A first attempted follow-up batch was stopped and excluded after detecting 99.8% aggregate host CPU utilization. An unrelated 48-worker CPU stress test was running. Its seven completed samples and interrupted run remain preserved as interference evidence, not algorithm results. The quiet batch starts after that workload and all builds/diagnostics finish. It checks host occupancy before each run and aborts on high sustained occupancy during a process. This episode does not establish that the same stress test affected the original morning measurements.

Every output from all four variants matches a previously semantically validated output byte-for-byte: stream matches the original and revised references; measure original matches its original reference and the other three variants match the revised reference. Thus copying does not cause the measure row-layout difference on this fixture. The difference persists with copying disabled, which isolates it to the timestamp-boundary correction among the changes that alter row selection. New replays compare complete persisted-file hashes after timing; they do not repeat the expensive row oracle already established above.

Measure: most rows still take the original path

The 474 copied blocks contain only 3,803 of 58,209,290 rows (0.00653%). Their large nonnumeric values account for 67,008,828 payload bytes (6.29% of payload, 6.27% of all input files) and 1,531,749,166 logical bytes. Byte coverage and row coverage are therefore very different.

Every one of the 113,281,124 numeric cell positions belongs to the 101,279 small input blocks. None bypasses normal decoding or encoding. These counts include null positions; they are not a count of nonnull values. No array cells occur in this measure fixture, so the trace array-cell optimization does not address this workload.

Normal mergeTwoBlocks handles 338,403,990 cumulative input rows across 69,134 calls: 5.81 times the original row count. Accumulated pending rows are processed repeatedly. This count is actual slice lengths, not an estimate from cached block byte-size metadata. The timestamp equality correction adds only 54 immediate merge decisions involving 53,775 input rows; subsequent grouping can still change the physical retention of older versions.

There is avoidable representation work in the numeric fallback:

  • banyand/measure/column.go:424 selects byte-backed cells for sequential reads.
  • column.go:474–476 builds [][]byte and converts each decoded integer to bytes.
  • column.go:283–305 converts those bytes back into integers before compression.

For example, a numeric column [10, 11, 12] becomes an integer slice, then three byte-backed cells for merging, then an integer slice again. Repacking numeric compression remains necessary when rows change. Those extra representations are a separate optimization opportunity. Extending the existing typed numeric form from query readers into merging would require proper null handling, version selection, ownership, and encoding support; passing a different decode flag alone is insufficient.

Measure: the previous-output check is overly conservative

Exclusive first-stop reasons from the real merge:

Reason Input blocks

The history check uses the greatest maximum timestamp written for the current series, not merely the last block’s maximum. A second diagnostic kept that guard enabled but evaluated all later checks for its rejected candidates. 2,826 of those 2,939 blocks passed every later check: 418,003,264 payload bytes, 9,069,017,372 logical bytes, and 50,067 rows. None contains numeric cells. The remaining 113 have other-head and/or own-successor overlap.

Consider already-written history [1,100], a full candidate [4,5], and all remaining input heads starting after 5. The current guard rejects [4,5]. Ordinary merging then loads it into an empty pending block and flushes it unchanged on the very next iteration (or at EOF). It never revisits [1,100]. This is why rejecting historical overlap is stronger than ordinary merging’s row-selection behavior.

The local equivalence argument depends on full, valid candidate metadata, no schema conflict or TopN, and strict isolation from every other head and the own source’s successor. A future equal timestamp must still reject copying. The history-specific unit test asserts the policy directly; it is not an end-to-end counterexample to that equivalence. Changing the policy needs full merge tests covering wide historical ranges, historical versions, missing columns, and future equality. The diagnostic did not remove the guard, so the additional 418 MB is an opportunity count, not a measured speedup or a released fix.

Independent checks show 333 of 392 full blocks overlap their own successor. These overlap flags are not exclusive and must not be added to the table. For example, blocks covering 10:00–10:10 and 10:05–10:15 need their rows merged, even if both blocks came from one input file.

Another 16 blocks / 8,258,506 payload bytes fail only the history check. The main stream limitation remains overlap, independently of that conservative check.

No encoded filters occur in the capture; filter preservation therefore adds no I/O here. Fallback reads and decodes payloads once; successor lookahead reuses the decoded metadata. The added eligibility checks and chunked copying are evaluated by the controlled comparisons above.

Profiles locate the remaining work

Separate CPU and allocation profiles use the same inputs and original/revised binaries. Profiles are diagnostic samples, not additional timing observations. CPU profiling includes the merge and brief measurement setup/teardown; allocation profiles cover the process without decoded-row validation. Their sampled allocation counts differ from exact runtime.MemStats counters, including Go’s treatment of tiny allocations.

In revised measure, cumulative CPU samples attribute 44.3% to ordinary block writing, 23.0% to loading block data, and 14.4% to mergeTwoBlocks. The encodeDefault subtree alone accounts for 37.9%. Cumulative call-tree costs contain their callees and must not be added to their child functions.

Allocation profiles expose two concrete costs left by the shortcut:

Revised measure allocation site Share
fastFieldAppend 41.0% of allocated bytes
fullFieldAppend’s field initialization 30.1% of allocated bytes
convert.Uint64ToBytes, reached through numeric decoding 97.3% of sampled allocation objects

The first two sites allocate approximately 39,482 MiB combined. This is cumulative allocation traffic, not resident memory and not a predicted speedup. Numeric conversion accounts for many small objects; field-list rebuilding accounts for most bytes. Both remain on the ordinary path used by almost all measure rows.

There is a confirmed existing buffer-reuse defect behind part of this traffic. column.reset keeps the inner value-slice capacity, and columnFamily.reset keeps the column array. But the first fullFieldAppend after reset constructs a fresh column with a nil value slice and overwrites that reusable slot (banyand/measure/block.go:1345–1350). The alternating pending and temporary blocks repeat this cycle. The same code exists in the baseline.

For example, a column can retain capacity for 8,192 rows, then allocate a new 100-row buffer after reset instead of using that space; later appends grow and copy it again. These lists hold byte-slice headers, not copies of every payload. Not all profiled append allocation is avoidable: new columns, schema padding, and genuine capacity growth still need storage. This diagnosis predates the implemented and benchmarked measure buffer-reuse change.

In revised stream, ordinary block writing accounts for 55.0% of CPU samples and loading block data for 22.9%. Zstd encoding is prominent. fastTagAppend and initial tag append together account for 39.8% of allocated bytes. With 333 full blocks overlapping their own successor, the shortcut cannot bypass most of that decode/merge/recompress work.

The observed stream elapsed-time reversal is therefore consistent with a small real computational saving obscured by system wait variation. The measure limitation is structural: a narrow whole-block shortcut, a conservative history restriction, and expensive ordinary merging. No copied-output corruption or large eligibility-check overhead was observed on these captures.

Follow-up work suggested by the evidence

  1. Test the history-check equivalence at the real merge seam, then consider removing that restriction while retaining fullness, future-overlap, own-successor, schema, and TopN checks. The 418 MB count makes this a concrete opportunity, but its resulting speedup has not been measured.
  2. Improve ordinary field-list buffer reuse and numeric representation. Preserve null versus empty values, numeric repacking, version selection, ownership, cancellation, and bounded retained capacity. Measure both overlapping numeric inputs and disjoint large-payload inputs; these are different workloads.
  3. Keep small-block coalescing. Relaxing it does not address the dominant stream limitation and would violate the intended output-size behavior.

Follow-up evidence and replay method

The earlier capture archive supplies the capture references and production source provenance.

The follow-up evidence records all 48 timing samples and four separate profiled runs. Its summary.json retains medians, ranges, paired differences, and exploratory bootstrap intervals; samples.json retains every unprofiled observation. Each run retains complete persisted-file hashes. postflight.json records 52 successful output-reference comparisons and unchanged production sources/baseline tracked tree.

Eligibility evidence includes: stream-eligibility-diagnostic, measure-eligibility-1, and measure-eligibility-counterfactual-1. The counterfactual diagnostic leaves the history guard enabled and confirms the output files remain identical. Pending logical-byte metadata can be stale after accumulating blocks; use the reported row-work counts, not those raw pending-byte counters, to quantify repeated merging.

The follow-up compares the frozen variants over eight stream rounds and four measure rounds, using fresh output directories and the same captured inputs. Builds, replays, profiling, and other heavy work run sequentially. All output files are compared with their validated reference outside the timed region. No production implementation changes were made during this follow-up analysis.
