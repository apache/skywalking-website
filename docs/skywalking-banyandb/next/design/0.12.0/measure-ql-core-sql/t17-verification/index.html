T17 typed ordering and compact top-k

Implemented on 8ee2a074 (T16), on PR #1412. T17 adds multi-key measure ORDER BY, budgeted full sorting and a finite-LIMIT heap using the same typed comparator. Committed as b13cdc6d. The measurements below describe the T17 verification revision. The subsequent legacy integration repair resolves its nine legacy-suite failures and passes 934/934 measure cases in each topology. The revised concurrent admission contract separates expected overload rejection from timed-query acceptance. Successful 100k/1m throughput is now explicitly deferred by the 2026-10-19 acceptance revision; the revised harness verification records the passing overload/recovery and timing-protocol checks; the historical measurements below are not rerun or reclassified by that repair.

Execution contract

The planner resolves source columns, visible aliases, ordinal references and completed aggregate/group outputs once. Each execution binds its own parameters, output types and mutable operator state. Computed timestamp aliases resolve ::TAG against the bound output container, including a timestamp and field sharing an alias. Alias names never enter a per-row lookup. Simple native timestamp and explicit index-rule ordering retain their existing paths.

native column batches
  -> WHERE
  -> grouping / aggregation
  -> HAVING and completed projections
  -> visible-tuple DISTINCT
  -> full sort or compact top-k
  -> OFFSET / LIMIT and visible output
  -> existing measure response

Optional stages are omitted when absent. Sorting sees every completed row after the preceding stages. Hidden WHERE inputs remain in the native scan projection; hidden ordering columns and aggregate calls survive until sorting and are then excluded from the response. DISTINCT permits only keys derivable from its visible tuple. LIMIT 0 performs no native scan.

Each key has independent ASC/DESC and NULLS FIRST/LAST. Defaults are ASC NULLS LAST and DESC NULLS FIRST. Integers compare exactly, strings and bytes compare byte by byte, and floating NaNs follow other non-null numerics in ascending order. Descending reverses non-null ordering without reversing NULL placement. Complete ties have unspecified relative order; test goldens include a unique tie key.

Unlimited results use cancellable heapsort with bounded comparator work. Finite LIMIT uses a max-heap of the best k = uint64(OFFSET) + uint64(LIMIT) rows, then sorts those candidates before slicing. The maximum supported sum is 8,589,934,590; it does not wrap uint32. Large offsets can approach full-sort retention.

Accepted candidates copy all reachable variable values, including strings, binary data, arrays and boxed protobuf values. Eviction reuses candidate cell slices. No candidate retains a source-batch owner. The shared tracker reserves key buffers, candidate descriptors/payload and output before allocation; candidate payload capacity is bounded by twice the live payload plus declared descriptor capacity. Boxed integer-array accounting includes native slice storage, because packed wire size can be much smaller than the cloned Go allocation. Full sort and top-k fail on budget exhaustion, with no spill or unbounded fallback. Close, cancellation and source errors release reservations and owners.

Generated endpoint verification

The independent finite model generates 32 sorting families with three bindings, 12 no-scan rejections and four resource specs: 48 T17 specs per topology. Cold/warm and bypass calls, forced full-sort parity, compact-budget controls and recovery queries produce 259 verification RPCs per topology. Readiness uses 12 QL-only pages; actual retry-inclusive counts are logged separately. No new case uses a native query for readiness or expected output.

Coverage includes F ordering and pagination, defaults and explicit NULL placement, hidden keys, alias precedence, exact int64s above 2^53, strings, NaNs, grouped and hidden aggregate keys, HAVING, bucket outputs, computed/ordinal grouping with AVG, visible DISTINCT, changed expression/time/page bindings, LIMIT 0, wide offsets, multi-batch input, cancellation, real candidate-budget errors and cleanup. Four cross-stage families use a hidden WHERE-only field in raw, computed, grouped and DISTINCT queries. The computed family also orders a qualified timestamp alias.

All 1,569 earlier generated cases and their expected responses are retained. Only the two obsolete T03 sorting-rejection queries change to genuinely absent, qualified keys; their original supported forms now have positive T17 witnesses. The complete artifact contains 1,695 cases. Its SHA256 is 3c2de0c2474d059b86402101535ebce27af5ed5418a6a9500aec443e2ddb84fe. The audited grammar fingerprint includes the new ORDER BY parser.

Focused four-CPU, 8-GiB Docker runs with no additional swap pass all 48 specs in both topologies. Each reports exactly 259 verification RPCs. Standalone readiness uses 12 calls; distributed uses 22 calls for the same 12 pages. Evidence is .omx/t17-generated-focused-{standalone,distributed}-v4.{log,json} and .omx/t17-generated-focused-v4-summary.json.

Public tests cover Prepare/Compile/Bind, WrapRaw/WrapSort and final response egress, with independent expected values. RED/GREEN regressions retain evidence for hidden WHERE projection, qualified timestamp aliases, invalid ordinals and under-accounted boxed arrays. Normal/tagged runtime and planner suites, focused race/ownership checks, liaison tests, the focused benchmark harness and make lint pass. Logs are .omx/t17-*-final.log, .omx/t17-planner-reviewed-*.log and .omx/t17-runtime-*.log.

Focused benchmark protocol

The kernel matrix has nine orthogonal shapes, avoiding a Cartesian expansion: 1/3/8 keys, deterministic random/ordered/reverse/tied input, narrow/wide payloads, k=10/100/1,000 and a large offset. Random source order uses an independent seeded permutation, including the one-key control. Standard-library tuple sorting is an independent oracle; full sort and top-k copy and return the same page. Actual key roots, row applications, kernel work, comparisons, retained candidates, descriptor/payload bounds and cleanup are checked before timing. A separate 32-batch probe poisons 1-MiB source buffers after copying one narrow candidate from each batch and checks owner and pool references.

The RPC comparison uses the same three-key SQL and ten-row page at 1,024 and 32,768 inputs. A querymetrics-only context forces reference full sorting through the existing liaison test hook; the default path uses top-k. The only additional workload is the planned composed filter/group/HAVING/order/page query with three changing bindings and 1/8/32 callers. No unrelated cache or older-ticket matrix is added. Warm-ups and retained timed samples check exact results; every timed call checks row count and contributes actual work and cleanup counters. Cache counters report observed reuse; they do not claim measured uncached planning savings.

These successful RPC sizes were fixed after admission, before final timing. The kernel supplies the 100,000-row algorithm comparison. Successful 100,000- and 1,000,000-row RPC throughput is not established: earlier tickets already record the unchanged native input-materialization ceiling, and T17 does not repeat that failing large-fixture approach or change the ceiling. See T16’s resource evidence. The PR #1412 legacy performance matrix is also not rerun; existing native golden tests establish correctness, not a new G1 latency verdict. These limits prevent closing the full planned performance acceptance from the focused sort measurements alone.

Final timing uses five fresh resource-limited Docker repetitions and prebuilt binaries. The kernel uses a normal build; RPC work counters require querymetrics. Source, binary, generated-artifact and retained-failure digests guard the run. The repeatable driver is test/integration/distributed/querybench/run-t17-frozen.sh; raw samples and CPU/heap profiles remain under .omx/bench-reports/qlb-t17-*-final.

Median top-k/full-sort time ratios are 0.0251 for k=10 and 0.0265 for k=100, below the specified 0.80 bound. The tuple baseline shallow-copies tuple descriptors and borrows fixture payloads. The public operator includes typed evaluation, owned candidate copies, tracked allocation, output and cleanup. Full sorting costs substantially more than that plain baseline, especially when the standard-library sorter recognizes ordered input. The comparison makes that cost visible; the full-sort path has no speed gate against the tuple baseline.

For both 100,000-row small-k controls, full sort performs 3,019,492 comparisons, below the 6,800,000 bound. Top-k performs 100,440 and 108,507. All three keys have 300,000 row applications, 294 actual root entries across 98 batches and 100,000 arithmetic-kernel rows. Candidate peaks are exactly 10/100; tracked sort peaks are 44,560/124,480 bytes, versus about 81.1 MB for full sort.

Large offsets retain much of the input: the 90,000-offset page holds 90,100 candidates, about 72.8 MB of tracked peak reservations, and approaches full-sort time. Reverse input causes frequent candidate replacements; the 1-KiB, k=1,000 case allocates about 34.1 MB cumulatively while retaining about 2.94 MB at peak. Bounded live state does not imply bounded total allocation over the entire scan. Every shape passes key-work, comparator, ownership, capacity and cleanup checks. The 1-MiB poisoned-source probe is correctness/resource evidence outside timing. Raw records, profiles and the passed numerical gate are retained in .omx/bench-reports/qlb-t17-kernel-final and kernel-summary.json.

Native concurrency limitation

The subsequent admission diagnosis reproduces this blocker at b4be414f and proves that 32 held fanout reservations exceed the configured shared pool. It preserves the original blocked performance verdict.

Untimed admission succeeds for the raw full-sort/top-k pair and composed 1/8-caller variants at both sizes, without changing the 256-MiB tracker setting. The 1,024-row 32-caller composed probe fails at native broadcast admission with ResourceExhausted: query memory pool exhausted. A separate forced-full-sort 32-caller control reproduces the same failure: 95 of 96 calls complete with exact results, and the rejected call never reaches WHERE, aggregation or sorting. Both controls restore all tracked resources to zero.

Native fanout reserves receive/parser buffers and part of the remaining allowance before opening streams. Concurrent reservations can exhaust the service-wide pool even though local sort candidates remain small. This is existing native input residency, not top-k retention. Protector policy, receive buffering and memory limits are unchanged. The same 32-caller failure is not repeated at the larger size.

The historical benchmark protocol required all five variants. The revised harness separates overload and recovery evidence from its four timed variants. The later criteria revision separates the 32-caller overload check; the following status describes the original protocol, not a new resource-gate verdict. An explicit retained failure report enables partial measurements of the four admitted variants while keeping the 32-caller variant marked blocked, with zero latency/allocation samples and the evidence digest. Overall status remains partial_known_32_blocked; it cannot be reported as a passed acceptance gate. Artifacts are .omx/t17-admission-1024-r3/t17-admission-1024.json, .omx/t17-admission-32768/t17-admission-32768.json and .omx/t17-concurrency-control/fullsort32-control/t17-admission-1024.json.

Compatibility boundary

T17 changes QL parsing/planning/execution and test infrastructure. Its diff from 8ee2a074 leaves protobuf definitions/generated APIs, native execution operators, transport/frame formats, persisted data and protector policy unchanged. The earlier approved T15 shared-buffer changes remain part of the parent history; they are not new T17 changes. Temporary-file spilling remains deferred.
