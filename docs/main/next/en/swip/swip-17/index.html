SWIP-17 Move the Native Trace Analysis from Java Listeners to TAL

Motivation

SkyWalking analyzed traces with two engines. Before this change, spans that arrived over OTLP were analyzed by TAL rules, which an operator can read and edit, and segments that SkyWalking’s own agents send were analyzed by Java listeners in the agent-analyzer module. Those listeners turned each span into OAL sources (Service, ServiceInstance, Endpoint, the relations, DatabaseAccess and others) for core.oal and the other .oal files, wrote the trace itself, and handed GenAI spans to their analyzers. Changing how a native span became a service, an endpoint or a relation, such as reading one more tag, was a Java change. The knowledge of what a span means lived in two places, written in two styles.

This change moved native analysis into TAL rules hosted by trace-analyzer and removed the production AnalysisListenerFactory SPI: every analysis of a native span is a rule file that the configuration activates. It was a port and nothing else:

  • No output change. For every segment, the rules send the same sources, with the same field values, in the same order, as the listeners did. They make the same stateful calls and side-effect calls in the same order, apart from the three exceptions below, and write the same log lines, debug included, under the script’s logger rather than the listener’s class name. OAL, storage, query, alarm and the UI were untouched, and so was every metric name.
  • No logic change. Each rule reproduces one listener branch by branch, including the cases where the Java failed a segment on malformed input. A difference found while porting was a defect of the port, not a fix to make on the way. A behaviour worth changing is changed afterwards, in its own change, with its own changelog line.
  • One exception, the evaluation sample. The listener sampled a GenAI span for evaluation during the span loop. The rule sends the sample as a GenAIEvaluationSample source in build {}, where a native rule makes all of its outputs, so the sample is taken after the segment’s last span. A segment that analyzes completely makes the same sample calls, with the same contexts, in the same order, only later. A segment that fails no longer takes the samples of the GenAI spans before the failure, see Failure behaviour the port keeps.
  • A second exception, adopted as a feature: the bare-host gateway match. OTLP and native rules share one isGateway, which also tries a bare host at port 80, the port gateways.yml gives an instance that names none. An HTTP client that omits the default port records its peer as the bare host, so a gateway listed once, at port 80, now matches it for native traces as it already did for OTLP ones; the listeners matched the exact address only. An address with a port is unchanged, and the debug lines follow the lookups made, see Failure behaviour the port keeps.
  • A third exception, a repeated tag key. An agent is not expected to send a tag key twice on a span. When it does, a native rule reads the first value everywhere, by name and in the one tag map. The listeners differed by place: the sources’ originalTags kept the last value, the GenAI analyses the first, and the cache analysis failed the segment; see Failure behaviour the port keeps.

The change added the native input, lifecycle constructs, outputs and functions needed by the port, summarized in What is new in TAL:

  • Native input: the sw-native input exposed the agent’s protobuf SpanObject as span, its SegmentObject through segment(), and the runner’s segment-wide results through functions. It is provided through TALSourceTypeProvider, the trace analyzer’s internal bridge to an input.
  • Settings: a rule reads a setting through a function, as it reads everything else an input or a module serves: agent-analyzer answers through a new typed service, and ai-evaluation contributes its two functions.
  • Outputs in build {}: a native rule makes its outputs in one deferred block. source {} hands an existing source to the source receiver, which dispatches it by scope to the OAL engine or to the dispatcher a module declares, documented as the adoption path for the existing source system; metrics {} declares a new metric, as it does in every TAL rule. source {} belongs to every input: an OTLP rule writes its records with it too, and TAL has no other record output.
  • Lifecycle constructs, plain assignment, typed values and log: what a per-span rule needs to reproduce a listener exactly, and to read like one.
  • Bridge functions: functions that call the caches, naming rules and lookups the listeners called. Other modules contribute their own functions through a new TALFunctionProvider extension point. Logic stays in the rules: a function reads a cache, a settings file or a lookup the rules cannot reach, or parses what TAL has no syntax for.
  • OTLP AI evaluation as a rule: the evaluation sampling of natively stored OTLP spans, which AIEvaluationSpanListener made in Java, moved to the shipped otlp-ai-evaluation rule, which sends the same GenAIEvaluationSample source as the native rule. As every OTLP rule, it sees the spans of the services that set service.layer=OTLP_GENERAL. Zipkin has no TAL input, so the listener kept the Zipkin path, OTLP spans stored as Zipkin spans included, unchanged; see Contributed by other modules.

The ported rules shipped under oap-server/server-starter/src/main/resources/tal/; this SWIP links those files, listed under The shifted rule files. A test module ran the removed listeners and native rules against the same constructed segments and compared their ordered outputs, stateful calls, log lines and failures at TAL’s boundary, with the three documented differences handled explicitly, following the precedent of the MAL and LAL move from Groovy to the v2 compilers.

Proposed Changes

The sw-native input type

SwNativeTALSourceTypeProvider implements TALSourceTypeProvider, the bridge between TAL and an input and the point an input is extended at, under the alias sw-native, beside OtlpTALSourceTypeProvider (otlp). It exposed the protobuf SpanObject directly, the wire object the listeners read, as an OTLP rule’s span is the OTLP Span. A rule reads the input from three places, and each value is in exactly one of them:

  • span is the SpanObject the agent sent;
  • segment() returns the span’s SegmentObject, as the agent sent it;
  • the segment functions return what the runner derived from the whole segment.

A field is read by its name, span.operationName, which compiles to the protobuf getter, getOperationName().

span. Value
operationName, peer, spanId, parentSpanId, startTime, endTime, componentId, isError, skipAnalysis the SpanObject fields
spanType the SpanType enum: Entry, Exit, Local, or UNRECOGNIZED for a value this OAP does not know; compared with a literal, span.spanType == "Entry"
spanLayer the SpanLayer enum, such as Database or FAAS, or UNRECOGNIZED; compared with a literal, span.spanLayer == "Database"
tagsList the tags in wire order, each with key and value; a key can repeat
logsList the logs in wire order, each with time and dataList, its key and value pairs in wire order
refsList the references in wire order, each a SegmentReference with its protobuf fields: refType (the RefType enum, CrossProcess or CrossThread), traceId, parentTraceSegmentId, parentSpanId, parentService, parentServiceInstance, parentEndpoint and networkAddressUsedAtPeer
segment(). Value
service, serviceInstance, traceId, traceSegmentId, isSizeLimited the SegmentObject fields, as the agent sent them
spansList every SpanObject of the segment, in wire order
Function Value
segmentStartTime(), segmentLatency(), segmentIsError(), segmentTags(), segmentSampled() the work of SegmentAnalysisListener.parseSegment, which the runner does once per segment before any rule runs, see below
segmentBytes() the SegmentObject serialized again by toByteArray(), what the Segment record stores; serialized at each call

No view classes or first-reference helpers were introduced. Where RPCAnalysisListener.parseEntry built once per reference or once without one, native-rpc-entry iterated span.refsList when the list was non-empty (!isEmpty(span.refsList)) and wrote a separate no-reference branch, including its own build body. The MQ rule selected the first reference with a guarded loop.

The runner does parseSegment’s work before the first rule’s first run, in its order, calling the same collaborators and writing the same log lines under the runner’s own logger:

  1. for each span in wire order: the start (restarting whenever the current minimum is 0) and end fold; isError = isError || SegmentStatusAnalyzer.isError(span) under agent-analyzer’s segmentStatusAnalysisStrategy; and the span’s tags that core.searchableTracesTags lists, within Tag.TAG_LENGTH, each equal key and value pair once, logging at debug a tag dropped for its length;
  2. the duration, capped at Integer.MAX_VALUE;
  3. TraceSegmentSampler.shouldSample, or an error segment under agent-analyzer’s forceSampleErrorSegment.

The runner exposed the derived start, duration, error state, searchable tags and sampling decision through segmentStartTime(), segmentLatency(), segmentIsError(), segmentTags() and segmentSampled(); segmentTags() is the read-only List<Tag> the Segment record stores. It performed that work for every non-empty segment, regardless of traceAnalysis, as SegmentAnalysisListener had been registered whatever it said; the end-time fold remained internal.

Each segment run held its own internal derived state, shared by the runs of every span of that segment, as TraceAnalyzer handed every listener the same SegmentObject; concurrent segments never share it. The rules read the immutable protobuf span and segment objects, so a rule cannot change a span or the segment. The shipped native-segment rule, as SegmentAnalysisListener did, stored the unmodified SegmentObject reserialized by segmentBytes() (toByteArray()) when a span 0 had initialized the record, and selected the record’s index fields; without a span 0 it kept the listener’s default record fields, a null dataBinary among them. The language did not restrict a custom source Segment {} to those fields; such a rule supplied the contents it stored.

What the listeners derived for one span alone, the rules write out where they need it, as the logic it is:

  • The service’s layer, identifyServiceLayer: FAAS for a span whose spanLayer is FAAS, GENERAL for any other. It is per span, not per segment: a FaaS function’s exit span over HTTP is GENERAL. From native-rpc-entry:

    def calleeLayer = "GENERAL" as Layer
if (span.spanLayer == "FAAS") {
  calleeLayer = "FAAS" as Layer
}

  • The span’s latency, (span.endTime - span.startTime) as Integer. The long conversion in TalValueConversions performed Java’s (int) cast, including overflow, and preserved the listeners’ conversion without the OTLP path’s clamping.

  • Once per segment, as SegmentAnalysisListener.build() ran once: a segmentDef guard on the segment’s first span in wire order, whatever its type, as native-segment writes it:

    if (buildQueued == null) {
  segmentDef buildQueued = true
  extractor {
    build {
      ...
    }
  }
}

The otlp input’s meta root, and the statements that overwrite it (service, instance, endpoint, layer), are not part of the sw-native input. The runner keeps the protocol-neutral SpanMetadata the engine needs internally, which no rule reads.

A native rule reads the native span in its own words. tag(key) answers the value of the first tag with that key, empty when there is none, and hasTag(key) whether there is one, where an OTLP rule reads attributes with attr and hasAttr. Where a listener iterated tags, the rule iterated span.tagsList; where it built a map of them, the rule calls tagMap(). tag() and tagMap() kept the first value of a repeated key, a documented difference. Native logs were exposed as span.logsList, with time and dataList on each log, what an OTLP span’s events are. A rule reads them as the list; no native listener read them.

Native spans carry no service.layer. The runner runs the sw-native rules on every span of every segment. The shipped native rules declared layer: GENERAL; compilation validated it, but native execution did not select rules by layer: the runner ran every loaded native rule on every span. A rule still sends FAAS where the listeners did, computing it as identifyServiceLayer did.

The settings a rule reads

A rule reads a setting through a function, as it reads everything else an input or a module serves; TAL has no settings root. A dynamic setting is read at the call, so a value the module changes later reads its new value.

  • agent-analyzer gained a typed service. It listed NativeTraceAnalysisConfig in AnalyzerModule.services() and registered it in prepare(), over its AnalyzerModuleConfig, as it already served UninstrumentedGatewaysConfig to trace-analyzer. The provider itself is never exposed, only what the service is written to answer, and the module pattern makes it mandatory: the module manager’s requiredCheck fails the boot when the provider does not register it.

    public interface NativeTraceAnalysisConfig extends Service {
    boolean isTraceAnalysis();                         // agent-analyzer.traceAnalysis
    int getMaxSlowSQLLength();                         // agent-analyzer.maxSlowSQLLength
    boolean isError(SpanObject span);                  // SegmentStatusAnalyzer under segmentStatusAnalysisStrategy
    boolean shouldSample(SegmentObject segment, int duration, boolean isError);
                                                       // TraceSegmentSampler, then forceSampleErrorSegment
    int slowDBAccessThreshold(String dbType);          // DBLatencyThresholdsAndWatcher.getThreshold
    int slowCacheReadThreshold(String type);           // CacheReadLatencyThresholdsAndWatcher.getThreshold
    int slowCacheWriteThreshold(String type);          // CacheWriteLatencyThresholdsAndWatcher.getThreshold
    boolean isNoUpstreamRealAddressAgent(int componentId); // AnalyzerModuleConfig.shouldIgnorePeerIPDue2Virtual
}

    The native input’s functions traceAnalysis(), maxSlowSQLLength(), slowDBAccessThreshold(type), slowCacheReadThreshold(type) and slowCacheWriteThreshold(type) read it, see Functions for the sw-native input; so does the shared isNoUpstreamRealAddressAgent(componentId), see Functions for every input; and so does the runner’s parseSegment work, through isError and shouldSample.

  • ai-evaluation contributes functions. Through a TALFunctionProvider that serves every input, the native native-ai-evaluation rule and the OTLP otlp-ai-evaluation rule among its callers, it contributes evaluationActive(), the decision its prepare() made, false when the judge configuration in ai-evaluation.yml is incomplete and it registered InactiveAIEvaluationService, and evaluationSampleRate(), from its AIEvaluationConfig. The provider reads both from a typed service, AIEvaluationSamplingConfig (active, sampleRate), which AIEvaluationProvider.prepare() registers and AIEvaluationModule.services() lists, as agent-analyzer serves its settings; the module provider itself is never exposed. It contributes nothing of the judge settings, the API key among them.

  • The core’s setting the runner’s parseSegment work reads, core.searchableTracesTags (SW_SEARCHABLE_TAG_KEYS): the runner read core.searchableTracesTags through the core’s ConfigService, as SegmentAnalysisListener read it, and exposed the resulting searchable-tag list through segmentTags().

  • Files with their own matching rules, gateways.yml and server-clusters.yml, stay behind the functions isGateway and clusterNameOrAddress.

How trace-analyzer runs the native rules

The runner reproduces TraceAnalyzer’s lifecycle callback for callback. TAL stays per span. A listener’s per-segment behaviour maps to two blocks and one kind of variable, each the counterpart of one Java mechanism:

TraceAnalyzer before the port The runner
A segment without spans returns at once Same
SegmentListener.parseSegment, before the spans The segment-function results, computed before the first rule ran
FirstAnalysisListener.parseFirst, on every span whose id is 0, before any other callback on that span, whatever its type first {} of every rule, in file order, on every span whose spanId is 0, before any rule’s regular run on that span, whatever its type
The entry, exit or local callbacks of every listener, in listener order, on every span in wire order Each rule runs, in file order, on every span in wire order; the rules select entry, exit and local spans through span.spanType. An unknown type matches none of those values, as no callback ran for it, and produces the runner’s error log, the line TraceAnalyzer wrote
A listener’s fields, alive for one segment segmentDef, a variable alive for one segment
build() of every listener, in listener order, after the last span build {} blocks. A block is queued when a span’s run reaches it. After the last span the runner runs the queued blocks rule by rule in file order, and within a rule in the order they were queued
NetworkAddressAliasMappingListener’s alias row, sent during the span loop writeNetworkAlias, sent at its statement
GenAIEvaluationAnalysisListener’s sample, taken during the span loop a GenAIEvaluationSample source {} in build {}, taken in the build phase: the one place the port moves a send, see Failure behaviour the port keeps
A listener’s log lines log statements, under the script’s logger org.apache.skywalking.trace.analysis.script.<script name>, and the functions that call the logging Java. The runner calls a compiled rule directly, not through TalDSL.evaluate, so the [TAL] rule=... debug line the OTLP path writes before each rule is not written for a native rule

Ordering follows from this. A Java builder is one queued build {} block: the parse callback filled it, build() formatted its names and sent its sources. A rule that formats names inside build {} therefore makes the NamingControl calls, whose results depend on EndpointNameGrouping’s per-service state and whose truncations log, at the same point and in the same number as the Java did. A rule that sends from build {} sends in the Java order.

Failures follow the Java too. The runner catches nothing, neither around a rule nor around the dispatch of a source it sends; the OTLP path catches around a rule. A rule that throws stops the segment at the same point a throwing listener stopped it, and the exception reaches ISegmentParserService.send and the receiver unchanged:

  • the gRPC handler counts and logs it;
  • the REST handler counts it and rethrows;
  • the Kafka fetcher’s handler catches only InvalidProtocolBufferException, so the exception leaves the handler.

A throw before the build phase means no queued block runs, and so no evaluation sample of the segment is taken. Everything already done stays done: alias rows sent, log lines written, and changes to the endpoint grouping’s state. A throw inside a build {} block, including one raised while a source is dispatched, stops the remaining blocks, and what was already sent stays sent.

The sw-native input has no retry dedup (dedupWindow does not apply), no network-alias pairing, and no persist {} or tag: the segment’s storage is the native-segment rule’s Segment record. prepareNetworkAlias, buildNetworkAlias, persist {} and tag are compile errors in a sw-native rule, and so are metrics {} and source {} outside build {}: a native rule makes its outputs there.

    • trace-analyzer declares among its required modules, when each is loaded, every module the rules reach, as it already declared agent-analyzer through getManager().has: agent-analyzer, the module each discovered TALFunctionProvider names, and every module a file of nativeTalFiles or talFiles lists under requiredModules, since requiredModules serves every input. New TAL section: Source

The port added source {} as the adoption path for existing sources, and as TAL’s one record output, for every input. It hands one source of the existing system to the source receiver, which dispatches it by its scope: to the OAL engine, the same object the SkyWalking agent path built for core.oal and the other .oal files, or to the dispatcher a module declares for it, as ai-evaluation declares one for GenAIEvaluationSample. It exists so that an analysis written in Java could move to TAL without changing what the existing system computes from it: every metric named in .oal keeps its name, its function and its number, and a record such as DatabaseSlowStatement is stored as before. A new metric is declared with metrics {} instead. The operator syntax was documented in the language page’s Source (existing system adoption), and the OTLP page’s Records describe the record the shipped OTLP rule writes.

source <Name> {
  <field> <expr> [as <Type>]
  ...
}

It compiled source names and setters against the registered source classes, required a time bucket and sent each source at its statement:

  • <Name> is the name OAL’s from() gives the source, the name of its @ScopeDeclaration: Service, ServiceInstance, Endpoint, ServiceRelation, ServiceInstanceRelation, EndpointRelation, ServiceMeta, EndpointMeta, DatabaseAccess, DatabaseSlowStatement, ServiceDatabaseSlowStatement, CacheAccess, VirtualCacheSlowAccess, MQAccess, MQEndpointAccess, Segment, TagAutocomplete, GenAIProviderAccess, GenAIModelAccess, GenAIEvaluationSample, and any source a module declares. These are the classes the source receiver dispatches by scope name, records such as Segment and DatabaseSlowStatement among them, and GenAIEvaluationSample, which no OAL script reads, see Contributed by other modules. Only a concrete source class with a public no-argument constructor qualifies; an unknown name is a compile error that lists the known ones.

  • Each field statement calls the source’s setter of that name, checked when the rule compiles. Keywords such as name, status, layer and endpoint work as field names here, and set the source’s field. The value is converted to the setter’s parameter type:

    • a number, a boolean, a string or a byte array as it is;
    • a Layer or an enum, such as RequestType or DetectPoint, as it is when the value already has that type (see Typed Layer and enum values), and from its name when it is a string. A literal name is checked when the rule compiles; any other string is converted when the rule runs, and a name that matches nothing fails the rule;
    • a List or Map field takes the list or map object as it is, such as tagList(), without copying it.
    • among a setter’s overloads, the one the value’s type fits best, as a function call chooses; a value that fits none, or several equally, is a compile error until an as settles it.

    A field the block does not set keeps the source’s constructor default: null for most objects, an empty list for Segment’s tags, a SideCar for Service’s.

  • timeBucket is required, minuteTimeBucket(...) for a metrics source and recordTimeBucket(...) for a record such as DatabaseSlowStatement, as the agent path set them. A source {} without it is a compile error.

  • Nothing is formatted implicitly. A name is stored as the expression gives it. A rule ported from the agent path calls formatServiceName, formatInstanceName and formatEndpointName where the Java called NamingControl.

  • The block holds field statements only. A value that depends on a condition is computed into a def first.

  • Where it is written. On sw-native, inside build {}: it is built and sent at its statement in the segment’s build phase, so a later failure in the same block leaves it sent. On otlp, in the extractor, sent at its statement as metrics {} is, so an abort {} or a failure later in the rule leaves it sent. OTLP has no sink {} and no outputType key: the output-builder lifecycle the OTLP input had in 11.1.0 was removed with them, and TALConfig has no outputType field, so an 11.1.0 rule file that sets it fails to load with the YAML binder’s unknown-property error until its record moves to a source {}. persist {} keeps the vote statements, sampler with rateLimit, enforcer {}, dropper {} and if, for the span’s own fate.

The shipped otlp-slow-sql rule writes its record this way, in its extractor after every abort {}, reproducing the SlowSQL builder field by field; DatabaseSlowStatementBuilder stays a LAL output builder only:

Other syntax additions

Assignment

<name> = <expr> [as <Type>]

Every input. TAL gained plain assignment to distinguish assigning a declared variable from declaring it: def declares a variable and = assigns it, so a reader tells the two apart. Before, TAL had only def, whose first use declared and whose later uses assigned, so a reassignment read like a second declaration.

def ok = true
if (span.isError) {
  ok = false
}
  • What it assigns. A variable declared by a def earlier in the rule’s text and in scope where the assignment stands, or by a segmentDef anywhere in the rule. A name nothing declares is a compile error, and so is a value that does not fit the variable’s type, the type of the value its declaration gave it.
  • Declaring before the branches. A variable the branches of an if assign is declared before them. A String, a Layer or an enum is declared with a typed null: def owner = null as String, def callerLayer = null as Layer. as String already kept null, and as Layer and as <Enum> keep it too: they convert nothing on the literal null and give the variable its type. Such a variable is null on the paths that do not assign it, the value it had when a branch’s def declared it. A number or a boolean is declared with a literal, def logicLatency = 0: as Integer, as Long and as Boolean turn null into 0 and false, as they did before, and the port did not change them.
  • Scopes. A def in a foreach body, in a build {} block or in a first {} run declares a variable of that iteration, block or run; = assigns it there, or assigns a variable of an enclosing scope.
  • Compatibility. A later def of an existing name retained its previous assignment behaviour, so existing rules remained compatible; otlp-general kept its form. The native rules used def for declarations and = for assignments.

foreach

foreach (<name> in <list>) {
  <the statements of the block foreach sits in>
}

foreach iterated a java.util.List, including span.refsList, span.tagsList and segmentTags(), with the element type resolved from the getter or function. The loop variable is typed to the list’s element type when the rule compiles, from the getter’s or function’s generic return type, so ref.parentService and spanTag.key are compile-checked chains. A def inside the body declares a variable of one iteration. It is declared again at each iteration, and it is not visible after the loop: that is how the Java built a fresh builder per reference. A variable declared before the loop and assigned inside it with = keeps its value across iterations. foreach is allowed wherever if is. Native rules used iteration to select a reference; list indexing such as span.refsList[0] and dedicated first-reference helpers were not introduced.

build

build {
  <def, assignment, if, foreach, abort, log, metrics, source>
}

sw-native only, inside extractor {}. The block is queued when the run reaches it and runs once after the segment’s last span, see How trace-analyzer runs the native rules.

  • What it sees. The run’s input, its span and its function context, as they were for that run, not the last span’s. The def values the run had when it reached the block, including the loop variables of the foreach it sits in, captured by value. The segmentDef values as they are when the block runs.
  • Its own variables. A captured value is the block’s own copy. caller = formatServiceName(caller) reads the copy and assigns it, as the Java formatted a builder’s field in place; the run and the other blocks do not see the change. A def inside the block declares a variable of that block.
  • Outputs. A sw-native rule makes its outputs here and nowhere else, each at its statement:
    • metrics {}, a new metric, as in every TAL rule. Its timestamp defaults to span.startTime, there being no meta, and a failure inside it skips that block, as it does everywhere: the first failure of a metric logs a warning, later ones log at debug. No shipped native rule declares one;
    • source {}, one source of the existing system, an OAL source, a record such as DatabaseSlowStatement, or GenAIEvaluationSample, which ai-evaluation’s dispatcher takes.
  • Deciding. A rule decides whether an output is made with if and abort {} before its statement, as the listeners decided in Java. The evaluation’s own sampling is the evaluation module’s policy, written in the rule at filter level from ai-evaluation’s settings through evaluationActive() and evaluationSampleRate(), where the listener asked the service.
  • Abort. An abort {} later in the same run withdraws the blocks that run queued. An abort {} inside a block stops that block only.

first

first {
  <the statements of a filter>
}

sw-native only, at filter level. It runs on every span whose spanId is 0, before any rule’s regular run on that span, whatever the span’s type, as FirstAnalysisListener.parseFirst did. It is a run of its own: it has its own def values, an abort {} in it ends that run only, and it shares only segmentDef values with the rule’s regular run.

segmentDef

segmentDef <name> = <expr>

sw-native only. A variable of the rule that lives for one segment, as a listener’s field did. It starts as null for each segment. The segmentDef statement declares it and assigns it each time it runs; <name> = <expr> assigns it too, anywhere in the rule, on any span of the segment; and the name reads it anywhere in the rule, before its first assignment included. Its storage belongs to one run of the runner, never to the compiled rule, so concurrent segments do not share it, and it is cleared when the segment ends, also when it fails.

writeNetworkAlias

writeNetworkAlias <address>

sw-native only. It sends, at its statement, a NetworkAddressAliasSetup with:

  • address the given address;
  • representService formatServiceName(segment().service);
  • representServiceNormal true;
  • representServiceInstance formatInstanceName(segment().serviceInstance);
  • the minute of the span’s start as its time bucket.

Formatting the service before the instance preserved the listeners’ naming-call order. This is the row NetworkAddressAliasMappingListener sent from an entry span’s cross-process reference. It sends the source and lets the dispatcher and the cache reload do the rest, without touching the cache. It does not use the OTLP path’s alias registration, which refuses an empty address or service and writes no instance.

The SkyWalking agent propagates the address the caller dialed in the sw8 header, so the callee alone has every fact of the row, and nothing waits for a caller’s half as the OTLP pairing does. The source has no @ScopeDeclaration name, so source {} cannot name it.

log

log <trace | debug | info | warn | error> "<message>" [, <expr>, ...]

Writes the message through SLF4J under the logger org.apache.skywalking.trace.analysis.script.<script name>, the script being the rule file without its extension, such as org.apache.skywalking.trace.analysis.script.native-rpc; the name is not configurable. Each {} is replaced by the next argument as SLF4J formats it. The arguments are evaluated only when the level is enabled, as the Java’s isDebugEnabled() guards did. It is allowed wherever a statement is. log, parseStatusCode, parseLongOrZero and parseIntOrZero log under the calling rule’s script logger; other helper diagnostics, such as those of toJson, toJsonArray and component, and the Java a function delegates to, such as the naming functions, log under their own class names.

Typed Layer and enum values

as converts a string to a Layer or to an enum a source takes, such as RequestType, DetectPoint, MQOperation, VirtualCacheOperation, TagType and GenAITraceRefType:

def calleeLayer = "VIRTUAL_CACHE" as Layer
def type = "HTTP" as RequestType

Layer is a registry, not a Java enum, and an unknown name fails. The compiler checked typed literals when the rule compiled: a Layer literal against the layers registered by then, those a rule file’s layerDefinitions register included, and an enum literal against the enum’s constants. Enum literals and built-in Layer literal casts compiled to their constants; other Layer conversions resolved the name at the statement. A def given a typed value has that type, so a misspelt name is a compile error where it is written, not a failure when its branch runs.

A Layer or an enum value compared with a string literal compares by name, and the literal is checked when the rule compiles: calleeLayer != "FAAS", operation == "Write". Enum comparisons with literals used enum constants, while Layer comparisons retained name semantics. String-literal equality compiled to equals.

Where each construct applies

OTLP and the native input read different spans and build differently: an OTLP rule reads attributes and events, overwrites the span’s metadata and votes on the stored span; a native rule reads tags and logs and makes its outputs in the segment’s build phase. So the language keeps what every input has, and TALSourceTypeProvider is the bridge between TAL and an input, and the point an input is extended at: TAL asks every input the same neutral questions, and each implementation answers in its own concepts. The input’s structure, its span, is primary and lives in the provider; functions are its helpers and extensions.

  • Its alias and its span, alias() and inputType(). inputType() supplied the Java type behind span, whose getters are the span.* fields; functions exposed additional input data, including the native segment and the OTLP resource and scope.
  • Its constructs, constructs().
  • Its functions, the provider’s own public methods that take the run first, named in the input’s own words: OtlpTALSourceTypeProvider’s attr, event, resource and the rest, SwNativeTALSourceTypeProvider’s tag, segment and the rest. Input providers gained bind(ModuleManager). The native provider retained service references bound once at startup, while per-run span and segment state remained in the execution context. Two inputs may each declare a function of one name, since no input has both.
  • Its helper functions, helperFunctions(): the helper function implementations its rules call beside its own functions, handed to the TAL kernel. Each is a TALFunctionProvider that answers through supportsInputType which inputs it serves, every input or a specific one, and must serve the input that hands it over; the kernel binds each once. The shipped inputs both hand over the logic functions and the configuration functions, which are the functions for every input.

The OTLP span’s remaining public reader, spanAttributes(Object), is a method of OtlpTALSourceTypeProvider, not of the bridge; an input that builds through span metadata as OTLP does extends that provider. The compiler loads every input, so a construct or a function a rule’s input does not have is reported as another input’s: the pairing root belongs to the inputs [otlp], not to this rule's inputType sw-native, or tag() is a function of the inputs [sw-native], not of this rule's inputType otlp. The rules compile at boot, so the misuse fails the boot, naming the file and the rule, as a rule on an unregistered layer does. A file that requiredModules leaves out is not compiled, and so not checked.

The function extension points

Rules called functions declared by their input provider, shared helper providers and loaded modules. An input’s own functions are its TALSourceTypeProvider’s public methods that take the run first; its helper functions are the TALFunctionProvider implementations its provider hands over, helperFunctions(). A module adds functions to an input through TALFunctionProvider too, which sits in server-core beside the sources, so a module can contribute functions without depending on trace-analyzer: ai-evaluation contributed evaluationActive() and evaluationSampleRate() that way. A module such as gen-ai-analyzer, which depends only on server-core while agent-analyzer depends on it, could not depend on trace-analyzer without closing a cycle.

  • Declaring. A provider names its module, states the inputs it serves with supportsInputType(inputType), which has no default, so every provider declares it, reaches its services in bind(ModuleManager), and is a class whose public methods TAL calls by name. The interface also holds the alias of the native input, SW_NATIVE_INPUT_TYPE, sw-native, which a provider of a module compares with, since the module cannot depend on trace-analyzer. A method whose first parameter is a TALFunctionContext receives the run there; an input’s own functions take trace-analyzer’s helper that implements it.
  • Resolving. The compiler resolves a call by name and the rule’s input, then by argument count. The compiler selected fixed-arity candidates before varargs and ranked argument fits as exact type, assignable supertype, numeric widening and scalar conversion. All numeric widenings had equal rank. Equal best scores caused a compile error until an explicit cast selected an overload. The result is typed from the chosen method’s return type, a nullable object or a generic List included.
  • Discovery and binding. A module’s providers are found through ServiceLoader; an input’s helpers come from its provider. Startup bound input providers, their helpers and providers of loaded modules once, in trace-analyzer’s start(), see Activation and startup.
  • Threading and names. A function name that two function classes serve for one input fails the boot, among an input’s own functions, its helpers and the modules’ providers, and so does one that takes an entity constructor’s name, such as service; a function that only another input has fails the rule that calls it, naming that input. Compilation installed the resolved function objects in fields of the generated rule instance. Runs called those fields directly; the objects held no segment-specific state and were shared safely across receiver threads.
  • The span as an argument. Native functions and contributed functions received the protobuf wire objects directly, through the run’s input or typed arguments. No native view interfaces were added to server-core; getter chains were compiled against the protobuf types.

Failure behaviour the port keeps

These Java paths failed a segment on input the agent should not send. The port reproduces each, through the functions above and the runner’s no-catch rule:

Java Input that fails The rule

Making any of them tolerant is a behaviour change, and so it was out of scope.

One read changed, by choice: a repeated tag key. An agent is not expected to send a tag key twice on a span, and a native rule reads the first value wherever it reads a tag by name, through tag(key) and the one tagMap(). The listeners differed by place: EndpointSourceBuilder.setTag kept the last value in the sources’ originalTags; GenAIMeterAnalyzer and GenAIEvaluationAnalysisListener kept the first; VirtualCacheProcessor’s Collectors.toMap threw, failing the segment before its cache.type guard. After the port a span with a repeated key keeps the first value in originalTags, and a cache span with one is analyzed rather than failing the segment. The GenAI analyses are unchanged. The checker’s fixtures cover these cases as differences of their own.

One match gained, as a feature: the bare-host gateway match. RPCAnalysisListener, EndpointDepFromCrossThreadAnalysisListener and NetworkAddressAliasMappingListener asked UninstrumentedGatewaysConfig.isAddressConfiguredAsGateway for the exact address. The native rules call the isGateway every input shares, which also tries a bare host at port 80, the port gateways.yml gives an instance that names none. A peer or a reference’s networkAddressUsedAtPeer written as a bare host, whose gateway the file lists without a port or at port 80, is therefore a gateway after the port and was not before: its relation goes to the gateway, and no alias row is written for it. An address with a port takes the one exact lookup the listeners made, with the same result and the same debug line. Two log differences ride along: a bare host writes UninstrumentedGatewaysConfig’s debug line twice, for the address and for it at port 80, and an empty address, which the listeners looked up and logged, is answered false without the lookup or its line. The checker’s fixtures cover these cases as differences of their own.

One failure path changed, by choice: when the evaluation sample is taken. GenAIEvaluationAnalysisListener sampled a GenAI span during the span loop. native-ai-evaluation sends the sample as a GenAIEvaluationSample source {} in build {}, where a sw-native rule makes its outputs, so it is taken in the build phase, after every earlier file’s blocks. The sampling decision and the tag reads stay in the span run, in their place.

  • A segment that analyzes completely makes the same sample calls, with the same contexts, in the same order. The sampling decision is a hash of the trace id, and the evaluation queue shares no state with the OAL engine, so the analysis itself does not change. What the evaluation service does with a call depends on its consumer threads, before the port as after it: whether a task of the same id is still pending, whether the bounded queue has room, and in which minute its counters move, which the OAP’s self-observability rules read as per-minute increases. A call made later can meet a different state, so a duplicate task, such as one from a re-sent segment, or a call that meets a full queue, can be accepted or skipped differently, and a counter can move in the next minute.
  • A segment that fails, on any span or in any earlier block, takes no sample. Before the port, the GenAI spans before the failure had theirs taken.
  • sample itself checks the context and counts a full queue rather than throwing, so taking the samples last stops nothing that would have run.

Verifying that the rules behave as the listeners did

The precedent

When MAL, LAL and the hierarchy rules moved from Groovy to the ANTLR4 and Javassist compilers (#13723, March 2026), the Groovy runtime stayed in the build as test-only *-v1-with-groovy modules under test/script-cases/script-runtime-with-groovy/, part of the default backend profile. mal-lal-v1-v2-checker and hierarchy-v1-v2-checker compiled the rules of their script directories with both engines and compared the outputs: MAL samples and entities, with a 0.001 numeric tolerance; LAL’s abort, save and standard fields, except for cases marked v2-only, which ran on v2 alone; the hierarchy matches. MAL’s .data.yaml expectations were generated from the Groovy output, and benchmarks compared the engines. After v10.4.0 shipped the new engines, #13782 (April 2026) removed the Groovy modules and the checkers, and kept v2-only execution tests asserting those expectations. Neither module existed when this work started.

This SWIP repeated that pattern with a stricter comparison: exact, ordered, and covering stateful calls, side effects and log lines at TAL’s output boundary, because the port’s claim is identical behaviour, not equivalent output. The evaluation sample’s sample calls were compared as a list of their own, and the repeated tag key and the bare-host gateway match as differences of their own.

What is compared

Each side ran every fixture with its own instance of every stateful collaborator: NamingControl with a real EndpointNameGrouping, NetworkAddressAliasCache, AnalyzerModuleConfig (whose component list parses, and warns, on first read), the latency-threshold watchers, the sampling policy, the searchable-tags watcher, the GenAI analyzer (v1 side) and a recording evaluation service, each kept for a whole multi-segment run as the OAP keeps them. Each side used its own analysis collaborators; source scopes were registered once, and the checker did not run stream processors. Logging was captured at TRACE except in the quiet-logs profile. The recording evaluation service records each call, answers shouldSample as the service it stands for answers, the active one from its sampling policy or the inactive one with false, and forwards no sample call. Only the v1 side asks it shouldSample; the new side decides in the rule from the same ai-evaluation settings, served by the module’s evaluationActive() and evaluationSampleRate(), which both sides are given. GenAIModelMatcher is loaded before either side runs, so its one-time load lines belong to neither. The comparison therefore covers each segment’s analysis up to and including its sample calls. What the evaluation service does with a call, inside sample (the pending-task dedup, the enqueue, the capacity counter) and after it on the consumer threads (the judge calls, result records and other counters), is the same code on both sides and outside this comparison. The v1 side is the old TraceAnalyzer with the old listener assembly. The new side is the runner with the default nativeTalFiles.

Each side produces one ordered event log per segment. Every event carries its phase (the parseSegment work, a first run, a regular run, the build phase), the wire index of the span for the phases that have one, and a canonical group: the Java listener or processor it belongs to, which on the new side is the rule that ports it (RPCAnalysisListener for the three native-rpc rules, and so on). The events are:

  1. every source sent, rendered at SourceReceiver.receive: its class, then every non-static field of the class and its superclasses, read by reflection and rendered recursively. Lists render in order, maps sorted by key, byte arrays by their content, enums and Layer values by name, and null stays distinct from empty. No method of the source is called, so NetworkAddressAliasSetup, whose getEntityId throws, renders like the others. A receive(null), which the Java made for an optional relation it did not build and the dispatcher ignores, is not an event;
  2. every NamingControl call, with its arguments and its result or exception, through a recording NamingControl;
  3. every call to the sampler, the searchable-tags watcher and the segment status analyzer, and every alias-cache read (findNetworkAlias, which calls NetworkAddressAliasCache.get), with its arguments and result. The alias cache is bounded (maxSizeOfNetworkAddressAlias) and a read updates its eviction order, so an extra or reordered read could change a later segment without changing this one’s sources;
  4. nothing for the evaluation’s sampling decision and the GenAI extraction, which the v1 side asks of Java and the new side computes in the rules: their effects are the events that follow, the GenAI sources and naming calls, the log lines and the sample calls, which are compared apart, see below. transferToSources builds the four GenAI sources; its naming calls are events through item 2;
  5. every log line: its level, message pattern and arguments, and its logger. A listener’s class logger and the logger of the script that ports it count as one, and so do TraceAnalyzer’s and SegmentAnalysisListener’s parseSegment lines and the runner’s own logger, and so do GenAIMeterAnalyzer’s and native-virtual-genai’s; a delegated Java class logs under its own name on both sides;
  6. the exception at the point it was thrown. Its class always matches. Its message matches for exceptions the listener code and its libraries raise by name, such as NumberFormatException, Gson’s exceptions and IllegalStateException; a NullPointerException’s helpful message names a variable and differs between the two sides, so only its class is compared.

Ordinary fixtures required equal ordered event logs and endpoint-grouping state, the state compared after each segment, failed ones included. Gateway and repeated-tag differences were checked explicitly, including the permitted log differences.

Evaluation samples were captured separately in call order, each context snapshotted at the call. Successful analysis compared the contexts against the live v1 reference, adjusted for documented differences. A failed native analysis was required to produce no samples; the v1 calls remained in the review dump.

The checker ended at TAL’s output boundary: emitted sources and evaluation records, stateful collaborator calls, log lines, exceptions and endpoint-grouping state. It did not execute OAL dispatch, stream processors, TopN buffering or persistence. No shipped native rule emitted metrics {}; a separate native-output unit test exercised that language path.

The OTLP outputType key, sink {} and the TALOutputBuilder interface were removed, and the shipped otlp-slow-sql rule writes its record with source DatabaseSlowStatement {}; TraceAnalyzerServiceImpl writes no record and no longer takes a ModuleManager. The OTLP evaluation sampling moved from AIEvaluationSpanListener to the shipped otlp-ai-evaluation rule, with SpanMetadata.traceStorage set by the OTLP receiver and matchGenAIModel and ai-evaluation’s two functions served to every input. The compiler work this needed beyond the grammar:
    • getters evaluated where they stand in the control flow and in their phase. A typed chain’s getter had been hoisted to the start of the method, which would dereference a null before the guard that protects it, or run a build-phase getter during the span run;
    • is getters for booleans, byte arrays, and generic element types carried through chains;
    • setters for objects, null, enums, Layer, byte arrays, lists and maps, without converting them to strings, with the best-fitting overload chosen as for a function call;
    • deferred build {} code with its captured input and values, and first {} as a run of its own;
    • segmentDef storage per segment and rule, outside the compiled rule;
    • input-aware compile checks that fail the boot, per Where each construct applies: each input’s TALSourceTypeProvider, the bridge of alias, input type, constructs(), helper functions, startup binding and the provider’s own functions, with the OTLP functions moved onto OtlpTALSourceTypeProvider and the native ones on SwNativeTALSourceTypeProvider, and supportsInputType on TALFunctionProvider;
    • rules loaded in configured file order and in-file order;
    • no catch on the sw-native path, around rules and around the dispatch of the sources they send, and no TalDSL.evaluate per-rule debug line on it;
    • the native runtime optimizations described under Performance.
  2. The port.
    • The sw-native input type over the protobuf SpanObject and SegmentObject, the runner with its parseSegment work, ISegmentParserService moved to trace-analyzer and its callers’ required modules, the data-generator tool’s configuration, the startup dependencies, nativeTalFiles, the shipped rule files, the functions of trace-analyzer, the GenAIEvaluationSample source in server-core and ai-evaluation’s dispatcher of it.
    • The listener framework, the listeners and the AnalysisListenerFactory SPI moved to trace-analysis-listener-v1, and the checker module was added.
  3. Documentation, per Documentation layout: the language page, the two input pages, the native setup and bundled-analysis pages, the menu, the moved anchors and their inbound links, the TALFunctionProvider Javadoc and changes.md.

Imported Dependencies libs and their licenses.

None in the distribution. The checker module uses JaCoCo (the Maven plugin and org.jacoco.core, EPL-2.0) at test time only; it is not packaged.

Compatibility

  • Outputs. The checker compared ordered outputs, collaborator events and logs, with explicit checks for repeated-tag handling, gateway matching and deferred evaluation samples: the same sources with the same fields in the same order, the same NamingControl calls, sampler calls, alias rows, log lines and failures. The evaluation sample calls are the same, with the same contexts and in the same order, for a segment that completes, though made after its last span, so what the evaluation service accepts can differ with its consumers’ timing; a segment that fails makes none, see Failure behaviour the port keeps.
  • Configuration.
    • One new setting, trace-analyzer.default.nativeTalFiles.
    • talFiles, traceAnalysis, the analyzer’s thresholds and every other existing setting kept their meaning. The default talFiles gained otlp-ai-evaluation; a deployment that sets talFiles (SW_TRACE_TAL_FILES) adds it to keep the OTLP evaluation sampling.
    • SW_TRACE_ANALYZER=- now stops the boot while the native trace receiver, which is on by default, or the Kafka fetcher is loaded, since trace-analyzer hosts the native analysis. An operator who removed the module to turn off OTLP analysis sets talFiles to empty instead, which the module already supported. With neither caller loaded, removing the module still works.
  • TALSourceTypeProvider, now the point an input is extended at, was reshaped. TALSourceTypeProvider gained constructs, helper functions and startup binding, with input functions declared as provider methods: alias(), inputType(), constructs(), helperFunctions() and bind(ModuleManager). OTLP-style custom inputs retained the constructs by extending OtlpTALSourceTypeProvider. spanAttributes(Object) remained overridable; scope attributes came from the execution’s supplied scope map, and custom event behaviour required overriding the public function methods rather than the former reader SPI.
  • Extension point. The AnalysisListenerFactory SPI was removed. A third-party listener moves to a rule file, plus a TALFunctionProvider for what TAL cannot read or call, and a source with its dispatcher for what it hands over that is not an OAL source, as ai-evaluation takes GenAIEvaluationSample. The TALOutputBuilder interface of 11.1.0 was removed, so a third-party builder written for it moves to a source and its dispatcher too. The module system did not change: agent-analyzer declares the NativeTraceAnalysisConfig service, and its provider registers it, as it registers UninstrumentedGatewaysConfig; ai-evaluation does the same with AIEvaluationSamplingConfig.
  • TAL. Additive, except the eight new keywords, which a user’s TAL rule can no longer use as def names, and the OTLP record output: the outputType key and sink {} were removed, so a custom OTLP rule file written for 11.1.0 that uses them fails to load until its record moves to a source {}, as the shipped otlp-slow-sql rule’s did. Plain assignment is additive: a later def of a declared name keeps assigning it.
  • Getters. On every input, a getter now runs where it stands rather than hoisted to the start of the rule. A chain that a hoisted getter dereferenced before its guard threw there, which on the OTLP path skips the rule for that span, with a warning the first time and at debug after; it now reaches the guard. The otlp input’s chains read protobuf getters, which never return null and have no side effects, so the shipped otlp-general rules behave the same. A custom input whose getters can return null may now pass a guard where it used to fail before it.
  • Log lines. Ordinary log levels, messages and arguments were preserved under the new logger names; the documented gateway lookups also changed their debug lines. The native analysis’s lines moved from the listeners’ class loggers to org.apache.skywalking.trace.analysis.script.<script name> and the runner’s own logger, so a logging configuration that sets a level for a listener class sets it for the script’s logger instead. GenAIMeterAnalyzer’s lines for native spans, its missing-model debug line and its parse warnings, moved to the native-virtual-genai script’s logger; it keeps logging under its own name for OTLP and Zipkin spans.
  • OTLP AI evaluation. A natively stored OTLP GenAI span is evaluated only when its service sets service.layer=OTLP_GENERAL, as otlp-ai-evaluation sees the spans of that layer; the listener evaluated every such span. A GenAI application sets the attribute on its resource, for example OTEL_RESOURCE_ATTRIBUTES=service.layer=OTLP_GENERAL. Zipkin spans, and OTLP spans stored as Zipkin spans, are evaluated as before. The rule runs with the other TAL rules, before the receiver checks the span listeners’ veto and the rules’ persist {} votes, where the listener ran inside the native store, after both: a span that a custom rule or listener keeps out of storage is evaluated now, though no shipped rule or listener vetoes a GenAI span. With dedupWindow above 0, a span an exporter sends again to the same node, while that node’s dedup set still holds it, is not analyzed again and so not evaluated again, even after the earlier evaluation finished; the listener sampled it again once the evaluation service no longer held the earlier task as pending.
  • Failures while a source is dispatched. On the OTLP input a source is dispatched at its statement, so a failure there fails the rule, which is caught and skipped: the slow-statement rule’s persist {} vote is then not counted, where the runner used to write the record after the rule and log a failed write, keeping the vote. A failure while an OTLP evaluation sample is dispatched no longer drops the span, as the native store’s catch did when the listener threw.
  • Storage, protocols, query, UI. No change.
  • Editing the rules. An operator who edits a native rule file, or reorders nativeTalFiles, changes the native analysis, as with any rule file. The shipped files and the default order are what the checker compares.
  • Distributions. The native TAL rules are compiled when the module starts. This change added no distribution precompilation and no boot-verification suite.
