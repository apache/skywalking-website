11.2.0

Project

  • Fix the release script on macOS: the source tarball carried an AppleDouble ._* entry and com.apple.provenance xattr headers for every file (the 11.0.0 source release has them, and GNU tar extracts them as stray ._* files with a warning per entry), the next-version PR step aborted because the single-branch release clone has no remote-tracking ref for the pushed branch, and the vote email left out the BanyanDB client proto submodule.
  • Move the BanyanDB that the e2e and integration tests run on to 88245d39, which carries apache/skywalking-banyandb#1476. Before it, a log query by trace ID missed stored lines that sat past the first limit + offset lines of their series in the read blocks (#14215), so a trace’s logs, or a page of them, came back short. A new IT suite in the BanyanDB storage plugin writes data through OAP’s own write paths and reads it back through every query DAO OAP reaches on BanyanDB, on the schemas OAP installs at boot (metrics included, generated from the shipped core.oal): streams, measures, index-mode measures, traces and properties, for paging, every filter kind, ordering, time-range edges, aggregation, top-N, index-mode updates and exact results. Its fixtures put matches at both ends of a series written in one bulk, so a filter applied after limit + offset loses a row, as it did for logs and GenAI evaluations (#14215) and for trace profiling’s segment read, which the previous BanyanDB also cut short. The BanyanDB Auth Rotation e2e case now matches the server’s unauthenticated refusal, which the new BanyanDB uses instead of Invalid credentials. The OTLP Trace e2e case asks for the newest trace that started over a minute ago: each service exports its own spans, so the newest trace was often still missing the frontend’s spans, and the new BanyanDB makes fresh spans searchable sooner, which turned an occasional failure into a steady one. The BanyanDB client ITs now match a 0.11 server: they expect API version 0.11, leave the server-stamped created_at out of schema comparisons (and check it survives a group update), leave the server’s own _deletion_task and _property_gossip groups out of a group count, and wait for a group deletion, which the server now finishes in the background. The unused test copy of bydb.dependencies.properties, a file 10.4.0 removed, is gone.
  • Make a failed integration test fail the build. Failsafe’s verify goal, which fails the build, ran in the verify phase that ./mvnw integration-test (the CI command) never reaches, so the Integration test job stayed green while ITs failed: 22 did on master, the 20 BanyanDB client ITs above, JDBCHistoryDeleteDAOIT (stale since ModelColumn requires a BanyanDB extension) and the Apollo one below. verify now runs in the integration-test phase, after the ITs.
  • Fix the flaky Elasticsearch client IT (ElasticSearchIT), whose failures stayed hidden until a failed IT failed the build (above). OpenSearch 1.0.0 moves to 1.3.20 and Elasticsearch 8.1.0 to 8.19.25, the latest of each line. On 8 of the 19 nightly runs since 2026-10-20 an OpenSearch 1.0.0 container never started, and the test waited out its five-minute startup timeout; every failed container’s only output is its start script stopping OpenSearch. The same output was reported upstream on 1.0.1, and its reporter saw it go away with the 1.1 image (opensearch-project/opensearch-build#504). Elasticsearch 8.1.0’s bundled JDK 17.0.2 crashed at startup on the runner’s cgroup v2 setup (NullPointerException in CgroupV2Subsystem) on 11 of the 13 nightly runs from 2026-10-07 to 2026-10-27, failing all eight of its tests each time. The OpenSearch 1.3.20 and 2.8.0 containers now run without the Performance Analyzer agent: the image starts its JVM beside the launcher’s, a JVM that starts beside another can print an hsperfdata lock warning, and the launcher takes that warning into its JVM options, so OpenSearch fails with Could not find or load main class Cannot (opensearch-project/opensearch-build#3821). The tested OpenSearch 1.x version in the storage docs is now 1.3.20.
  • Test Zipkin and the span-attached events of eBPF profiling on Elasticsearch and OpenSearch, and the DAOs of the BanyanDB storage. The Zipkin e2e case on OpenSearch runs in CI again, now on OpenSearch 3.0.0: it pinned OpenSearch 1.2.0, so it lost its CI job when #13715 dropped the OpenSearch 1.x e2e tests, and had not run in CI since. New slow ITs write through OAP’s own write path and read back through the Elasticsearch storage’s DAOs and the trace and Zipkin query services, on Elasticsearch 8.18.8 and 9.3.0 and OpenSearch 2.8.0 and 3.0.0 with OAP’s default storage settings, and on Elasticsearch 9.3.0 and OpenSearch 3.0.0 with logic sharding and custom routing. For Zipkin they check every search filter against a near miss, spans on and just outside each time bound, traces spread over two daily indices, the traces a limit keeps, reads by trace ID, and the service, remote service and span name lists; for span-attached events, every event of the traces asked for across scroll pages, in start-time order, and each event on its own span in the trace and Zipkin query results. The BanyanDB storage ITs now cover every DAO the plugin registers except the history delete, a no-op because BanyanDB applies its own TTL, with new ITs for the span-attached event query, traces read with their events (through the DAOs and the trace and Zipkin query services), the batch DAO that routes each write to its bulk, and dropping a measure, an index-mode measure, a stream, a trace and a property, and a unit test for the TTL status query.
  • Move the BanyanDB that the e2e and integration tests run on to 8efdf0ca, which carries apache/skywalking-banyandb#1479 and apache/skywalking-banyandb#1481, and run the three BanyanDB ITs that waited for them again. Before it, an index-mode measure ordered by time came back in index order, so findEndpoint with a limit did not return the newest endpoints (#14218), and a pre-built TopN query applied AGGREGATE BY after keeping one value per entity, so the MEAN OAP asks for returned each entity’s best value in the range instead of its mean (#14217).
  • Test every DAO of the JDBC and Elasticsearch storages, as the BanyanDB DAOs are: each IT installs the schema the way OAP does at boot, writes through OAP’s write path, reads through the DAO the storage provider registers, and compares whole results, with near misses, rows on and just outside the time bounds, paging and order. The JDBC ITs run on PostgreSQL 13 and MariaDB 11.4, with rows on both sides of midnight so a read crosses two day tables. The Elasticsearch ITs run on Elasticsearch 8.18.8 and 9.3.0 and OpenSearch 1.3.20, 2.8.0 and 3.0.0, and on Elasticsearch 9.3.0 and OpenSearch 3.0.0 with logic sharding and custom routing. They are nested ITs of one IT per server, so each server starts once, and every model they install must be found installed again, as on OAP’s next boot.
  • Test every request the Elasticsearch client sends for OAP on a server of each request format it picks by version: Elasticsearch 6.8.23, 7.7.1 (legacy index templates), 7.8.0 and 7.17.29 (composable index templates), 8.19.25 and 9.3.0, and OpenSearch 1.3.20, 2.8.0 and 3.0.0. Elasticsearch 7.4.2, 7.15.0 and 8.9.0 and OpenSearch 2.4.0 leave the client IT, whose formats the versions above cover. Each server starts once for all its tests, so the job takes about 3 minutes instead of 20.
  • Run every e2e case that stores in Elasticsearch on Elasticsearch 8.18.8 and 9.3.0; only the storage case ran on 9.3.0 before. The OTLP native trace case also keeps Elasticsearch 7.15.0. Outside the CI matrix, these cases default to 8.18.8.
  • Fix the mini-program e2e log check failing about 1 run in 4: a log whose content held a ' broke the YAML of the expected log.
  • Bump graphql-java 21.5 → 25.2 and graphql-java-tools 13.0.1 → 14.0.1. graphql-java shades its own copy of guava into its jar, and 21.5 carries guava 32.1.2-jre, which scanners report as vulnerable even though the OAP manages its standalone guava to a newer version; 25.2 shades guava 33.8.0-jre. graphql-java-tools 13.0.1 calls a graphql-java parser method that 24.0 removed, so it moves to 14.0.1, which pulls in Kotlin 2.1.20; its jackson-module-kotlin is pinned to the managed jackson version. 25.x is also the graphql-java line armeria-graphql 1.34.2 is built against.
  • Bump Armeria 1.34.2 → 1.43.1, and the managed versions of the libraries it is built against to its versions: gRPC 1.80.0 → 1.85.1, Jackson 2.18.12 → 2.22.4 (jackson-annotations 2.22, which has no patch versions since 2.20) and Micrometer 1.16.8 → 1.17.2. graphql-java stays at 25.2, though armeria-graphql 1.43.1 is built against 26.1: graphql-java 26 removed graphql.schema.idl.DirectiveInfo, which graphql-java-tools 14.0.1, its latest release, still uses to build the schema, so the OAP failed to boot on it. Armeria 1.43.1 builds a gRPC stub on the client factory named in the stub’s options instead of the one newClient is called on, so the Cilium fetcher’s stubs fell back to Armeria’s default factory and connected without the fetcher’s TLS settings, and the fetcher read nothing from a TLS Hubble endpoint; it now names its factory in the options. Armeria 1.43.1 also applies a tlsCustomizer after tlsNoVerify(), so the Cilium fetcher’s CA replaced the trust-all setting and Hubble’s certificates failed the host name check. The fetcher now verifies Hubble’s certificates against SW_CILIUM_FETCHER_CA_FILE_PATH, without checking host names; before, tlsNoVerify() won and the CA file was ignored, so a CA file that does not sign Hubble’s server certificates no longer connects. jackson-datatype-jsr310, which Armeria pulls, is pinned to the managed Jackson version; it was 2.20.1 beside Jackson 2.18.12. Transitively, brotli4j moves 1.20.0 → 1.24.0, micrometer context-propagation 1.2.0 → 1.2.1, proto-google-common-protos 2.63.2 → 2.64.1 and animal-sniffer-annotations 1.26 → 1.27, and LatencyUtils is no longer shipped.

OAP Server

  • Fix the Cilium fetcher dropping or double-reading Cilium nodes. The Peer notify stream, the cluster watcher and the 10-second refresh timer rebuilt the shared node list without a lock, which could open two flow streams for one node or keep a closed node as in use. A node closed when this OAP’s share of nodes moved away was reused, still closed, when the share moved back (e.g. after scaling the OAP cluster out and back in), so that node went unread while the assignment lasted. A Receiver-role OAP on a ZooKeeper, Consul, Nacos or etcd coordinator never finds itself in the cluster list and, when Cilium nodes and other OAPs were listed, threw on every refresh; it now skips Cilium fetching quietly, as the Mixed and Aggregator OAPs share all Cilium nodes among themselves.
  • Fix the gRPC alarm hook throwing a NullPointerException on every alarm until OAP restart: once an alarm fired while no gRPC hook was configured (at boot, or after the hooks were removed through dynamic configuration), adding a gRPC hook later broke it. Also shut down the client of a gRPC hook removed from the configuration.
  • Fix the Cilium fetcher silently stopping a Cilium node’s flow stream. When a stream failed and was retried (e.g. a Cilium agent restart), the ended stream’s thread interrupt stayed registered on its node, so closing that node later (e.g. when the OAP cluster scaled) interrupted whichever stream the pooled thread then ran for another node, and an interrupted stream is treated as closed and never retried. A stream that started just as its node closed was also never interrupted. Each stream now registers before it opens and deregisters when it ends, and a closed node refuses new registrations.
  • Fix one gRPC alarm hook with a malformed target, such as http://host or host:port as the host, stopping every gRPC hook: building its client threw and aborted the whole gRPC callback on each alarm, and a malformed target in the static alarm settings stopped OAP from starting. That hook is now skipped with an error log, at boot too, and a hook whose target becomes malformed keeps its previous client.
  • Make the cluster coordinator’s watcher list safe for a watcher that registers after the coordinator started, as the Cilium fetcher does: the plain list shared with the coordinator’s notify thread could throw a ConcurrentModificationException there or miss the new watcher.
  • Add the OTLP_VIRTUAL_GATEWAY layer: the OTLP trace analysis draws a gateway listed in gateways.yml as a node of this layer, the OTLP counterpart of the agent path’s VIRTUAL_GATEWAY, as it already puts the databases, caches and brokers it conjectures under the OTLP_VIRTUAL_* layers. The shipped tal/otlp-general.yaml uses it; a copy of the rule file made from an earlier release keeps drawing VIRTUAL_GATEWAY until it is updated.
  • The analysis of SkyWalking agents’ traces now runs as Trace Analysis Language (TAL) rules, like the OpenTelemetry trace analysis, and can be read and extended the same way. The rule files are listed in the new trace-analyzer setting nativeTalFiles (SW_TRACE_NATIVE_TAL_FILES) and ship under config/tal/. Metrics, topology and stored traces stay the same, apart from two edge cases: where a tag is looked up by its key, such as the tags kept with service and endpoint metrics, a span that repeats the key now gives its first value (and a cache span with a repeated key is now analyzed instead of failing its segment), and a segment that fails during analysis no longer sends AI evaluation samples.
  • Uninstrumented gateways in gateways.yml now also match a bare host in SkyWalking agents’ traces, as they already did in OpenTelemetry traces: an address written without a port, as an HTTP client records it when it omits the default port, matches the gateway listed at port 80 (or listed without a port), so a gateway is listed once. Port 443 is not inferred: a bare host is retried only at port 80, so a gateway configured at port 443 matches only an address that includes :443.
  • SW_TRACE_ANALYZER=- now stops the OAP from starting while the native trace receiver (on by default) or the Kafka fetcher is enabled, because they need the trace-analyzer module to analyze agents’ traces. Without either of them, it still turns off the OpenTelemetry trace analysis as before.
  • The log lines of the agent trace analysis moved to new logger names, one per rule file: org.apache.skywalking.trace.analysis.script.<file>, such as org.apache.skywalking.trace.analysis.script.native-rpc for what RPCAnalysisListener logged. Update a logging configuration that names one of the old listener classes; the Native Trace Analysis doc lists the new names.
  • TAL rules can now assign a declared variable with =, loop with foreach, write log lines with log, use typed layer values (as Layer), and limit a rule file to loaded modules with requiredModules; more functions, toJson and toJsonArray among them, can be called anywhere a value goes. A custom rule that uses source, foreach, in, build, first, segmentDef, writeNetworkAlias or log as a variable name has to rename it, as they are now keywords.
  • TAL rules write their records with source {}, such as source DatabaseSlowStatement {}, which an OpenTelemetry rule sends where it is written. The OpenTelemetry rules’ outputType key and sink {} block are removed: a custom rule file written for 11.1.0 that uses them fails to load until its record moves to a source {}, as the shipped otlp-slow-sql rule now writes its slow statement.
  • AI evaluation samples natively stored OpenTelemetry spans (otlpTraceStorage: otlp) through the new otlp-ai-evaluation TAL rule, listed in trace-analyzer’s default talFiles, instead of its span listener. It is declared for the OTLP_GENERAL layer, like the other shipped OpenTelemetry rules, so it sees only the spans of services that set service.layer=OTLP_GENERAL: a GenAI application whose spans should be evaluated sets that resource attribute, for example OTEL_RESOURCE_ATTRIBUTES=service.layer=OTLP_GENERAL. A deployment that sets talFiles (SW_TRACE_TAL_FILES) adds otlp-ai-evaluation to it. Zipkin spans, and OpenTelemetry spans stored as Zipkin spans, are sampled as before.
  • Fix a webhook alarm hook not being posted when the alarm also names a hook of another type: the webhook callback looked up the other hook’s name in the webhook settings and threw a NullPointerException. Depending on the hook names, the webhook was never posted (for example webhook.default with gRPC.default), or an error was logged on every alarm.
  • Add alarm.default.grpcTimeout / SW_ALARM_GRPC_TIMEOUT, the deadline in seconds of each gRPC alarm hook stream (default 10, which was the fixed deadline before).
  • Record gRPC alarm hook deliveries on the alarm delivery self-observability metrics (alarm_http_delivery_total and alarm_http_delivery_latency_seconds) with hook_type=gRPC, so the OAP dashboards show the gRPC hook as one more channel.
  • Keep the trace an OTLP log was written in: the OTLP log receiver now stores a record’s trace_id as the log’s trace ID, which it dropped before, and its span_id in a new otlp_span_id column. The log query’s TraceScopeCondition takes otlpSpanId to read the logs one OTLP or Zipkin span wrote, which the numeric spanId cannot name, and a LAL rule sets it with otlpSpanId, an output field of the default output type. An existing BanyanDB log stream and Elasticsearch log index gain the column at boot.
  • A log query’s relatedTrace is one of traceId alone, traceId with segmentId and spanId for a SkyWalking native span, or traceId with otlpSpanId for an OTLP or Zipkin span; any other mix is refused rather than read. This also refuses two forms accepted before: segmentId without spanId, which read the logs of a whole segment, and spanId without segmentId. The debugging query API refuses segmentId, spanId or otlpSpanId without traceId, which it ignored before.
  • Fix OAP running out of memory when receiving Envoy metrics from a large mesh. Converting a metric name (replacing . and / with _) went through a cache capped at 1,000 names, but Envoy metric names embed the upstream cluster name, so a large mesh has many more of them. The cache kept missing, and every miss took a lock shared by all Envoy metrics streams; the blocked streams piled up gRPC threads until OAP ran out of memory. The name is now converted directly, without a cache or lock.
  • Breaking Change — JDBC storage (MySQL, PostgreSQL): the log tables gain the otlp_span_id column, and OAP adds it at boot only to the current day’s table. Every other existing log table keeps its old shape — including the next day’s, when OAP had already created it before the upgrade — and inserting a log into one fails, for logs from every source. When upgrading, add the column to the existing log tables, ALTER TABLE log_<yyyyMMdd> ADD COLUMN otlp_span_id VARCHAR(64);, or drop them, which deletes their logs, so OAP creates them anew.
  • Fix the Apollo configuration dropping items of a grouped dynamic configuration: when one item of a group changed, the others were removed from OAP until they changed again or OAP restarted, because the change listener passed on only the changed keys while the receiver treats what it is given as the whole group. The listener now reads the whole group again.
  • BanyanDB: fix the instance hierarchy query, which read the service hierarchy measure and failed with fail to query measure, so an instance’s hierarchy never loaded.
  • BanyanDB: fix alarm paging without an entity filter: the offset was applied in the query and again to its result, so every page after the first came back empty.
  • BanyanDB: fix the eBPF profiling analysis reading at most 100 rows of a schedule per 10-second window, and counting a row uploaded on a window’s end in both windows. It now reads every row of [begin, end), as Elasticsearch and JDBC do.
  • BanyanDB: fix trace profiling’s thread-snapshot reads. A batch included its upper sequence, so the analysis counted a snapshot on a batch boundary twice; a snapshot lost its language, so a Go profile read back as Java and the Go analysis found nothing; and an empty range returned the integer extremes instead of -1.
  • Fix a trace-profiling thread snapshot’s time bucket being narrowed to int when read back, which overflowed for any second-level bucket.

  • BanyanDB: an init or default-mode OAP now applies additive schema changes (new columns, tags or fields) at boot to every measure, stream and trace, as it already did on JDBC and Elasticsearch, so a metric whose storage only gained columns in an upgrade no longer stays disabled. A breaking change (a removed or retyped column, a different entity) is still refused at boot. The OAP logs one line for each storage resource outcome its installers record: DEBUG when unchanged, INFO when created, updated or dropped, ERROR when an incompatible change is refused; the storage plugins log the DDL they run at DEBUG.
